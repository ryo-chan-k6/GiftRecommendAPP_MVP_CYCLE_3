## 2. 目的

本ドキュメントは、MVP 受入テストおよび受入に接続する品質検証の **実行環境方針** を正本化する。

以下を固定する。

- 受入の実施環境（何を合格証跡として認めるか）
- local / Layer2 / 簡易 stg / prod の役割分担
- レコメンド品質の多様データパターン検証の置き場
- 簡易 stg の DB 構成方針
- 後続のリリース判定・システム／品質計画への前提

インフラの実構築手順、受入ケース全量、本番デプロイ手順は本ドキュメントの範囲外とする。

---

## 3. 採用方針（Human 確定）

**MVP の受入は簡易 stg 必須とする。local + Layer2 のみで受入完了とはしない。**

補足（同日 Human 確定）:

- 実運用想定の多様なデータパターンによるレコメンド品質の人手・探索検証は **簡易 stg** で行う
- 本番同等フルスペック環境は、品質探索の入場条件にはしない（性能・規模・構成起因リスクの検証用に後段で強化する）
- local は Mock 中心・外部 API live は許可制。prod / stg の secret を local に置かない

## 4. 選択肢比較

| 案 | 概要 | コスト | 漏洩・誤接続リスク | 正本整合 | 判定 |
| --- | --- | --- | --- | --- | --- |
| A. フル stg 必須 | 本番同等構成を受入・品質の前提にする | 高 | 低 | MVP としては過大（環境設計書は簡易 stg を許容） | 不採用（後段強化） |
| B. local + Layer2 で受入代替 | stg を作らず受入証跡を個人環境／GHA ephemeral に寄せる | 低 | **高**（local live・secret・再現性） | **弱い**（全体テスト計画書 §7.8 は staging） | 不採用 |
| **C. 簡易 stg 必須 + Layer2 は別ゲート** | 受入・多様パターン品質は簡易 stg。システム／固定品質は Layer2 | **中（抑えめ）** | **低〜中** | 受入観点では整合（注記あり） | **採用** |

注記（案 C）: 受入観点では全体テスト計画書 §7.8（staging）と整合する。一方、システム／固定品質の実施環境は全体計画 §7.5（staging）とテスト環境設計書（Layer2）の記述が並走しているため、全面「正本整合・強い」とはしない。詳細な矛盾解消は後続のシステム／品質計画 Task で整理する。

## 5. 環境役割分担

| 環境 | 主用途 | 受入証跡 | 外部 API | 備考 |
| --- | --- | --- | --- | --- |
| local | 実装・単体・探索（Mock 既定） | **数えない** | 原則 Mock。live は明示フラグ＋許可制 | prod / stg secret 禁止 |
| Layer2 GHA | システムテスト／レコメンド品質の **固定ケース・自動メトリクス** | 受入の代替にしない | 原則 fixture mock | ephemeral DB。再現性ゲート |
| **簡易 stg** | **受入**、多様パターンの人手品質評価、受入前通し確認 | **ここに限定** | 限定 live（明示時のみ） | MVP は簡易構成で可 |
| prod | 提供・リリース後 smoke／監視 | 受入には使わない | 通常運用のみ | テスト連打禁止 |

## 6. 検証種別と環境の対応

| 検証種別 | 環境 | データ |
| --- | --- | --- |
| 固定評価ケース・自動メトリクス・回帰 | Layer2（`test-reco-quality.yml` 等） | fixture / 固定ケース |
| **実運用想定の多様なデータパターン・人手妥当性** | **簡易 stg** | 本番準拠の匿名化・縮小カタログ＋評価ケース |
| 受入シナリオ（主要導線・UX・運用確認） | **簡易 stg** | 受入用シナリオ＋上記カタログ |
| 契約・異常系・観測性 | Layer1/2 ＋ 簡易 stg | 環境に依存しにくい観点を優先 |
| 性能・負荷・本番構成起因 | 後段の本番相当強化 stg（本方針の簡易 stg 外） | 規模が効く観点 |
| 本番 smoke | prod | 最小確認のみ |

本表は全体テスト計画書 §7.7 の細分化である。全体計画本文への反映は後続 Task の候補とし、本 Task では並走注記に留める。

レコメンドは UX の単一正解が無いため、**探索（広く見る）** と **ゲート（リリースを止める条件）** を分ける。

- ゲート: 重大破綻なし、NG 混入なし、予算違反なし、Critical / High = 0 等（全体テスト計画書 §7.7・§12.2）
- 探索: 簡易 stg 上の多様パターン人手レビュー。見切れ分は残課題としてリリース判断に載せる

## 7. 簡易 stg の DB 構成方針

### 7.1 物理構成

| 項目 | 方針 |
| --- | --- |
| インスタンス | **stg 専用 PostgreSQL 1 本**（Supabase なら stg 用プロジェクト 1 つ） |
| 分離 | prod / local / Layer2 ephemeral と **共有しない** |
| スキーマ | **prod と同一 migration** |
| Replica / 分析分離 | MVP 簡易 stg では **持たない**（後段強化） |
| Redis / Object Storage | 環境ごとに分離（環境設計書 §7） |

### 7.2 論理構成（同一 DB 内）

```text
stg DB（1本）
├─ A. master（relationship / occasion / semantic_config 等）
├─ B. カタログ縮小セット（item / feature / embedding 等）
├─ C. 評価セット（evaluation_dataset / case / run）
└─ D. 実行ログ（recommendation_run / result / feedback）
```

受入用と品質評価用で **物理 DB を分割しない**（MVP）。破壊的な再取込実験が常態化する後に、必要なら評価専用インスタンス追加を検討する。

### 7.3 データ投入

| 区分 | 方針 |
| --- | --- |
| カタログ | 本番準拠の **匿名化・縮小版**（環境設計書 §7.3・§11.2） |
| 評価ケース | `evaluation_dataset` 等で version 管理し、合格証跡に dataset／カタログ版を残す |
| prod データ | **直接共有・生ダンプ投入しない** |
| 件数目安 | 多様性が確保できる縮小セットとする。具体件数は Human が別途確定してよい |

多様パターンの本丸は DB 本数ではなく、**B（カタログ分布）＋ C（評価ケース）** である。

### 7.4 接続

- api / reco / batch の stg 実行は、いずれも **同一の stg `DATABASE_URL`** を参照する
- secret 実値は docs・Issue・PR・ログに記載しない

## 8. local 利用の最低ルール

受入を stg に寄せても、local からの本番誤接続は別途封じる。

1. prod / stg の secret を local `.env` に置かない
2. 外部 API live は明示フラグ等で既定 off
3. Agent / CI / Layer2 の live も既定 off
4. **受入証跡は簡易 stg 上の結果のみ有効**。local 合格は受入に数えない

詳細な変数名・Secrets 名の正本は [環境変数定義書](../../06_実装設計/cross_cutting/環境変数定義書.md) / [環境変数運用手順](../../15_運用・改善/運用手順/環境変数運用手順.md)。構築手順は [簡易stg構築手順](../../15_運用・改善/運用手順/簡易stg構築手順.md)。
