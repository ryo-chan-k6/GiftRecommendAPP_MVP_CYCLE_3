# プロジェクトディレクトリ構成定義書

## 1. 目的

本ドキュメントは、Gift Recommendation Service MVP におけるプロジェクトディレクトリ構成を定義する。

本プロジェクトでは、設計成果物、実装コード、テスト資材、DB定義、API契約、コード定義、CI/CD、バッチ実行定義、AI活用資材を同一リポジトリで管理する。

そのため、以下を明確にする。

```text
- 実行コンポーネントごとの配置
- shared_logic の配置
- API契約定義の配置
- OrvalによるAPIクライアント生成物の配置
- コード定義・enum相当定義の配置
- 設計成果物の配置
- テスト成果物の配置
- テストコード・fixture の配置
- DB migration / seed / DDL の配置
- GitHub Actions workflow の配置
- Issue / PR テンプレートの配置
- GitHub運用補助スクリプトの配置
- Cursor / AI開発支援ルールの配置
- AI作業プロンプトの配置
```

---

## 2. 基本方針

| 方針                                                       | 内容                                                                                             |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Monorepo構成とする                                         | web / api / reco / batch / shared_logic / docs / tests を1リポジトリで管理する                   |
| 実行単位は `apps/` 配下に置く                              | web、api、reco、batch はそれぞれ独立した実行コンポーネントとして扱う                             |
| 共通ロジックは `packages/` 配下に置く                      | reco / batch から共通利用する shared_logic はアプリではなく共通パッケージとして管理する          |
| API契約は `packages/contracts/` 配下に置く                 | OpenAPI、schema などのAPI契約定義を共有資材として管理する                                        |
| Orval生成物は呼び出し元コンポーネント配下に置く            | web → api の生成クライアントは `apps/web`、api → reco の生成クライアントは `apps/api` に配置する |
| コード定義は `packages/code-definitions/` 配下に置く       | Feature、Semantic、mode、status、phase、error_code などのコード体系を機械可読な形で管理する      |
| TypeScript共通型は `packages/shared-types/` 配下に置く     | web / api で共有する型定義を管理する                                                             |
| 設計成果物は `docs/` 配下に集約する                        | 設計〜テスト〜運用改善までの成果物を工程別に管理する                                             |
| `docs/` 配下のみ日本語ディレクトリ名を採用する             | 設計成果物の可読性を優先し、番号プレフィックス付き日本語ディレクトリで管理する                   |
| 実行資材系ディレクトリは英語名とする                       | `apps/`、`packages/`、`tests/`、`scripts/`、`.github/` 等は自動化・CLI利用を考慮して英語名とする |
| テストケース・テスト結果は設計書と分ける                   | テスト方針・定義・計画と、具体的なテストケース・結果を分離する                                   |
| テストコードは `apps/*/tests/` または root `tests/` に置く | 単体・モジュール内テストは各app配下、横断テストはroot `tests/` に置く                            |
| DB定義は `db/` 配下で管理する                              | migration、seed、DDL、検証SQLを実装資材として管理する                                            |
| マスタ投入データは `db/seeds/` 配下で管理する              | Relationship、Occasion、Pair、Feature、Semantic等の初期投入データを管理する                      |
| 外部API fixture は再利用可能な形で管理する                 | 実API疎通テストで取得した代表レスポンスをMock / Fixtureに反映する                                |
| GitHub運用資材は `.github/` 配下で管理する                 | Issue Template、PR Template、Actions workflow、GitHub運用補助スクリプトを配置する                |
| GitHub Actionsは `.github/workflows/` で管理する           | CI、CD、Batch、PR自動化、Slack通知 workflow を配置する                                           |
| GitHub関連スクリプトは `.github/scripts/` 配下に置く       | GitHub Actions、Issue、PR、Projects、Slack通知に閉じた補助スクリプトを配置する                   |
| 汎用スクリプトは `scripts/` 配下に置く                     | 開発、DB、Batch、運用補助などGitHubに依存しないスクリプトを配置する                              |
| Cursor専用ルールは `.cursor/` 配下で管理する               | Cursor Rules / Skills を配置する                                                                 |
| 汎用AIプロンプトは `prompts/` 配下で管理する               | ChatGPT / Cursor / Claude Code 等で再利用する作業指示テンプレートを配置する                      |
| AI開発支援ルールを明示する                                 | AIが参照すべきルール・プロンプト・docs正本をリポジトリ内に保持する                               |

## 4. ルート直下の役割

| パス                  | 役割                                                                  |
| --------------------- | --------------------------------------------------------------------- |
| `README.md`           | プロジェクト概要、起動方法、主要リンクを記載する                      |
| `AGENTS.md`           | AI Coding Agent / Cursor向けの開発ルールを記載する                    |
| `package.json`        | monorepo全体のnpm script、workspace管理を行う                         |
| `pnpm-workspace.yaml` | pnpm workspace対象を定義する                                          |
| `orval.config.ts`     | OpenAPIからAPIクライアントを自動生成するためのOrval設定を管理する     |
| `.env.example`        | 必要な環境変数名を管理する。secret値は記載しない                      |
| `apps/`               | 実行可能なアプリケーションコンポーネントを配置する                    |
| `packages/`           | 複数コンポーネントから利用される共通資材を配置する                    |
| `db/`                 | DB migration、seed、DDL、SQLを配置する                                |
| `docs/`               | 設計成果物・テスト成果物・運用改善成果物を配置する                    |
| `tests/`              | 横断的なテストコード、E2E、技術検証、fixtureを配置する                |
| `scripts/`            | 開発・DB・Batch・運用補助スクリプトを配置する                         |
| `infra/`              | デプロイ先・インフラ関連設定を配置する                                |
| `prompts/`            | AI作業指示テンプレートを配置する                                      |
| `.github/`            | GitHub Actions、Issue Template、PR Template、GitHub運用資材を配置する |
| `.cursor/`            | Cursor Rules / Skills などAI開発支援設定を配置する                    |

## 5. `apps/` 構成

`apps/` は、実行可能なコンポーネントを配置する領域とする。

```
apps/
├─ web/
├─ api/
├─ reco/
└─ batch/
```

| パス          | 役割                                      |
| ------------- | ----------------------------------------- |
| `apps/web/`   | Next.js フロントエンドを配置する          |
| `apps/api/`   | Webフロントエンド向けPublic APIを配置する |
| `apps/reco/`  | FastAPIベースの推薦内部サービスを配置する |
| `apps/batch/` | Pythonバッチ処理を配置する                |

---

## 5.1 `apps/web/`

`apps/web/` は、Next.js フロントエンドを配置する。

```
apps/web/
├─ src/
│  ├─ app/
│  ├─ components/
│  ├─ features/
│  ├─ generated/
│  │  └─ api/
│  ├─ lib/
│  └─ styles/
│
├─ tests/
│  ├─ unit/
│  └─ component/
│
├─ public/
├─ package.json
└─ README.md
```

| パス                 | 役割                                                        |
| -------------------- | ----------------------------------------------------------- |
| `src/app/`           | Next.js App Routerの画面・ルーティングを配置する            |
| `src/components/`    | 汎用UIコンポーネントを配置する                              |
| `src/features/`      | 機能単位のフロントエンド実装を配置する                      |
| `src/generated/api/` | Orvalにより生成された web → api 用APIクライアントを配置する |
| `src/lib/`           | API client wrapper、共通utility等を配置する                 |
| `src/styles/`        | グローバルCSS、スタイル関連資材を配置する                   |
| `tests/unit/`        | web単体テストを配置する                                     |
| `tests/component/`   | UIコンポーネントテストを配置する                            |
| `public/`            | Next.jsが静的配信する公開ファイルを配置する                 |

### `apps/web/src/generated/api/` の方針

`apps/web/src/generated/api/` は、Orvalによる自動生成物の配置先である。

```
OpenAPI public-api.yaml
  ↓
Orval
  ↓
apps/web/src/generated/api/
```

生成物は手動編集しない。API仕様変更時は、OpenAPIを更新し、Orvalにより再生成する。

`apps/api/` は、ExpressベースのPublic APIを配置する。

```

├─ src/
│  ├─ index.ts
│  ├─ routes/
│  ├─ modules/
│  ├─ generated/
│  │  └─ reco-client/
│  ├─ infrastructure/
│  │  ├─ db/
│  │  ├─ reco-client/
│  │  └─ logger/
│  ├─ middlewares/
│  └─ config/
│
├─ tests/
│  ├─ unit/
│  ├─ contract/
│  └─ integration/
│
├─ package.json
└─ README.md
```

| パス                              | 役割                                                                  |
| --------------------------------- | --------------------------------------------------------------------- |
| `src/index.ts`                    | APIアプリケーションのエントリポイント                                 |
| `src/routes/`                     | Webフロントエンド向けPublic API route定義を配置する                   |
| `src/modules/`                    | API側ユースケース単位の処理を配置する                                 |
| `src/generated/reco-client/`      | Orvalにより生成された api → reco 用Internal APIクライアントを配置する |
| `src/infrastructure/db/`          | DB Repository / SQL呼び出しを配置する                                 |
| `src/infrastructure/reco-client/` | 生成されたreco-clientを利用する呼び出しラッパーを配置する             |

| `tests/unit/`                     | api単体テストを配置する                                               |
| `tests/contract/`                 | API契約テストを配置する                                               |
| `tests/integration/`              | api内部またはapi周辺の結合テストを配置する                            |

### `apps/api/src/generated/reco-client/` の方針

`apps/api/src/generated/reco-client/` は、Orvalによる自動生成物の配置先である。

```
OpenAPI internal-reco-api.yaml
  ↓
Orval
  ↓
apps/api/src/generated/reco-client/
```

MVPでは、まず `apps/web/src/generated/api/` を優先し、`apps/api/src/generated/reco-client/` は必要に応じて導入する。

生成物は手動編集しない。Internal API仕様変更時は、OpenAPIを更新し、Orvalにより再生成する。

packages/

| ---------------------------- | -------------------------------------------------------------------------- |

## 6.1 `packages/shared-logic/`

`shared_logic` は、reco / batch の双方から利用される共通ロジックである。

```
packages/shared-logic/
├─ pyproject.toml
├─ src/
│  └─ shared_logic/
│     ├─ feature/
│     ├─ semantic/
│     ├─ meaning/
│     ├─ embedding/
│     ├─ versioning/
│     └─ utils/
│
├─ tests/
│  └─ unit/
│
└─ README.md
```

| パス          | 役割                                                                            |
| ------------- | ------------------------------------------------------------------------------- |
| `feature/`    | Feature生成、Feature正規化に関する共通ロジックを配置する                        |
| `semantic/`   | Semantic Concept、Feature Rule適用に関する共通ロジックを配置する                |
| `meaning/`    | Social / Symbolic射影に関する共通ロジックを配置する                             |
| `embedding/`  | Embedding入力生成、Embedding関連共通処理を配置する                              |
| `versioning/` | semantic_config_version、feature_normalization_version等のversion扱いを配置する |
| `utils/`      | shared_logic内の共通utilityを配置する                                           |

```
reco  ─┐
       ├─ packages/shared-logic/
batch ─┘
```

recoとbatchの両方から呼び出すため、`apps/reco` や `apps/batch` の内部には置かず、`packages/shared-logic/` に配置する。

```

## 6.3 `packages/code-definitions/`

`packages/code-definitions/` は、実装・seed生成・テスト・型生成で参照するコード定義を管理する。

ここでいうコード定義には、プログラム言語上のenumだけでなく、設計・DB・API・ログ・テストで共通利用する識別子体系を含める。

```
packages/code-definitions/
├─ semantic/
├─ application/
├─ state/
├─ batch/
├─ error/
└─ README.md
```

| パス           | 役割                                                                                             |
| -------------- | ------------------------------------------------------------------------------------------------ |
| `semantic/`    | Feature、Semantic Concept、Semantic Rule、Feature Rule等の意味定義・意味空間関連コードを配置する |
| `application/` | recommendation mode、source type等のアプリケーション横断コードを配置する                         |
| `state/`       | recommendation run status、phase、batch run status等の状態・フェーズコードを配置する             |
| `batch/`       | batch job type等のバッチ処理コードを配置する                                                     |
| `error/`       | error_code等のエラーコード定義を配置する                                                         |
| `README.md`    | code-definitions配下の管理ルールを記載する                                                       |

### コード定義の位置づけ

`packages/code-definitions/` は、以下のような値の機械可読な定義元として扱う。

```
- Feature code
- Semantic concept code
- Semantic rule code
- Feature rule code
- Recommendation mode
- Recommendation source type
- Recommendation run status
- Recommendation run phase
- Batch run status
- Batch phase
- Batch job type
- Error code
```

### Feature / Semantic の扱い

Feature / Semantic は単なるenumではなく、レコメンドロジックの意味空間を構成する意味定義マスタとして扱う。

設計上の定義は `docs/` 配下に保持し、実装・seed・テストで利用する機械可読定義は `packages/code-definitions/semantic/` 配下に配置する。

## 16. まとめ

本プロジェクトでは、以下の構成を基本とする。

```
apps/       実行コンポーネント
packages/   共有ロジック・契約・コード定義・共通型・fixture
db/         DB migration / seed / DDL / SQL
docs/       設計成果物・テスト成果物・運用改善成果物
tests/      横断テスト・技術検証・E2E・非機能・品質評価
scripts/    開発・DB・Batch・運用補助
infra/      インフラ・デプロイ関連設定
prompts/    AI作業指示テンプレート
.github/    Issue / PR Template・CI/CD・Batch workflow・Slack通知・GitHub運用補助
.cursor/    Cursor Rules / Skills
```

特に重要な設計判断は以下である。

```
- reco / batch は apps 配下に分離する
- shared_logic は packages/shared-logic 配下に切り出す
- API契約は packages/contracts 配下に集約する
- コード定義は packages/code-definitions 配下に集約する
- OpenAPIからOrvalでAPIクライアントを自動生成する
- Orval生成物は呼び出し元コンポーネントの generated 配下に配置する
- 生成コードは手動編集しない
- docs 配下のみ日本語ディレクトリ名を採用する
- docs 配下は番号プレフィックス付きで工程順に管理する
- tests 配下は実行資材として英語ディレクトリ名にする
