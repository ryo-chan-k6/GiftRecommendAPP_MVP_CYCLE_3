# プロジェクトディレクトリ構成定義書

## 1. 目的

本ドキュメントは、Gift Recommendation Service MVP におけるプロジェクトディレクトリ構成を定義する。

本プロジェクトでは、設計成果物、実装コード、テスト資材、DB定義、API契約、コード定義、CI/CD、GitHub運用資材、AIエージェント運用資材を同一リポジトリで管理する。

そのため、本ドキュメントでは以下を明確にする。

- 実行コンポーネントの配置
- 共通ロジック・共通型・コード定義の配置
- API契約定義とOrval生成物の配置
- DB migration / seed / DDL / SQL の配置
- docs配下の工程別成果物配置
- docs/00\_共通 配下の共通資料配置
- GitHub Actions workflow と仕様書の配置
- Issue / PR テンプレートの配置
- Git hookの配置
- Cursor / AIエージェント設定の配置
- prompts / Task Definition / AI補助テンプレートの配置
- ai-logs の配置
- worktree の扱い
- ディレクトリ間の責務分担

---

## 2. 本ドキュメントの位置づけ

本ドキュメントを、プロジェクト全体のディレクトリ構成に関する正本とする。

AIエージェント運用に関するディレクトリ構成も、本ドキュメントに統合して管理する。

| 対象                               | 方針                                                                |
| ---------------------------------- | ------------------------------------------------------------------- |
| プロジェクト全体のディレクトリ構成 | 本ドキュメントで定義する                                            |
| AIエージェント運用ディレクトリ構成 | 本ドキュメントに統合する                                            |
| Git hook配置                       | 本ドキュメントで定義する                                            |
| 個別ディレクトリ内の詳細ルール     | 必要に応じて各ディレクトリのREADMEで補足する                        |
| 具体的な運用ルール                 | Projects運用ルール、Issue運用ルール、ブランチ運用ルール等で定義する |
| AI作業定義の仕様                   | Task Definition設計書で定義する                                     |
| Cursor Command / Agent の仕様      | Commands設計書、AI Agent定義設計書で定義する                        |

## 3. 基本方針

| 方針                                                       | 内容                                                                       |
| ---------------------------------------------------------- | -------------------------------------------------------------------------- |
| Monorepo構成とする                                         | web / api / reco / batch / packages / docs / tests を1リポジトリで管理する |
| 実行単位は `apps/` 配下に置く                              | web、api、reco、batch は独立した実行コンポーネントとして扱う               |
| 共通資材は `packages/` 配下に置く                          | shared logic、API契約、コード定義、共通型、fixtureを管理する               |
| DB migration 適用正本は `supabase/` 配下に置く               | Supabase CLI 管理の migration を配置する（[マイグレーション方針書](../../06_実装設計/database/マイグレーション方針書.md)） |
| DB設計資材は `db/` 配下に置く                              | seed、DDL、検証SQLを管理する（`db/migrations/` は Phase2 以降使用しない） |
| 設計成果物は `docs/` 配下に集約する                        | 事業構想からリリース・運用改善まで工程別に管理する                         |
| docs配下のみ日本語ディレクトリ名を採用する                 | 設計成果物の可読性を優先する                                               |
| 実行資材系ディレクトリは英語名とする                       | CLI、自動化、AIエージェント実行時の扱いやすさを優先する                    |
| GitHub運用資材は `.github/` 配下に置く                     | Issue Template、PR Template、workflow、GitHub運用補助スクリプトを配置する  |
| Git hookは `.githooks/` 配下に置く                         | commit-msg等のローカルGit hookを配置する                                   |
| Cursor専用設定は `.cursor/` 配下に置く                     | Commands、Agents、Rules を配置する                                         |
| 汎用AIプロンプトは `prompts/` 配下に置く                   | ChatGPT / Cursor / Claude Code 等で再利用する定義を管理する                |
| AIログは `ai-logs/` 配下に置く                             | Issue化前、例外、横断影響、実験ログのみを保存する                          |
| workflow仕様書は `docs/06_実装設計/github_actions/` に置く | YAML実装前に仕様書を作成する                                               |
| GitHub Actions workflowは `.github/workflows/` 直下に置く  | サブディレクトリは作らず、ファイル名prefixで分類する                       |
| worktreeは原則リポジトリ外に置く                           | 並列AI作業領域をGit管理対象と混在させない                                  |
| `.cursorrules` は採用しない                                | Cursor向けルールは `.cursor/rules/` を正とする                             |

## 7. `apps/` 構成

#### 7.3.1 API-INT と MOD-RECO の責務境界（パス）

識別子 Epic（`API-INT-*` / `MOD-RECO-*`）の `epic_scope` は、以下のパス境界を正とする（詳細は [成果物一覧×Task Definition化方針書](../AIエージェント運用/成果物一覧×Task%20Definition化方針書.md) §3.5、[recoディレクトリ構成不整合棚卸し](../../06_実装設計/reco/recoディレクトリ構成不整合棚卸し.md)）。

| 識別子種別 | 所有パス（例） | 除外（forbidden 例） |
| ---------- | -------------- | -------------------- |
| `API-INT-*` | `apps/reco/src/reco/api/**` | `apps/reco/src/reco/application/**`（モジュール/Orchestrator 層）、`apps/reco/src/reco/domain/**` |
| `MOD-RECO-*` | `apps/reco/src/reco/application/**`、`domain/**`、`pipeline/**` 等（当該モジュール範囲） | `apps/reco/src/reco/api/**`（エンドポイント層は API-INT Epic） |

旧表記 `apps/reco/src/app/**`・`apps/reco/src/modules/**` は使用しない。

### 8.1.1 OpenAPI ファイルレイアウト方針（Phase0 確定 / Phase1 実装）

Phase0（[実装フェーズ実行プロセス設計書](../プロジェクト管理/実装フェーズ実行プロセス設計書.md) §6.1）で、OpenAPI **実ファイル**のレイアウト方針を以下に定める。実 YAML の作成・更新は Phase1（API Contract 基盤）の Contract Task で行う。

| 項目 | 方針 |
| ---- | ---- |
| 正本ルート | `packages/contracts/`（`openapi/` ルートディレクトリは使わない） |
| MVP 既定レイアウト | **集約 YAML**: `packages/contracts/openapi/public-api.yaml`（Public API）、`packages/contracts/openapi/internal-reco-api.yaml`（Internal Reco API） |
| 代替案（Phase1 で採否判断） | **リソース別分割**: 例 `packages/contracts/openapi/paths/<resource>/` 配下に path 断片を置き、ビルドまたは Orval 入力前に集約する |
| Phase1 着手前の確認 | 集約 YAML 継続かリソース別分割かを Contract Task 起票時に Human Review で確定する（未確定のまま識別子 Epic の `epic_scope` に `openapi/paths/**` を正本として書かない） |
| 旧表記の扱い | ドキュメント・Definition に残るルート `openapi/paths/**`・`docs/openapi/openapi.yaml` 参照は Phase0 Task ②③で是正する |

## 19. worktree配置方針

AIエージェントの並列作業では、Git worktreeを利用して作業領域を分離する。

worktreeはリポジトリ本体内ではなく、原則としてリポジトリ外に配置する。

例：

```text
workspace/
├─ gift-reco/
└─ gift-reco-worktrees/
   ├─ docs-task-111-api-design/
   ├─ feature-task-112-api-implementation/
   └─ test-task-113-api-unit-test/
```

| 方針                         | 内容                                   |
| ---------------------------- | -------------------------------------- |
| リポジトリ外に置く           | Git管理対象と混在させない              |
| 1 Branch = 1 worktree        | 複数AIエージェントの作業領域を分離する |
| 作業完了後に削除する         | 不要な作業領域を残さない               |
| `.gitignore`にも保険を入れる | 誤配置時のcommitを防ぐ                 |

## 23. 禁止事項

以下は禁止する。

- docs配下に工程番号なしの工程ディレクトリを追加すること
- 運用改善成果物を `14_リリース/` 配下に配置すること
- リリース成果物を `15_運用・改善/` 配下に配置すること
- PoC成果物を正式成果物として扱い、該当工程へ再整理せず参照し続けること
- AIエージェント運用系ドキュメントを `docs/00_共通/プロジェクト管理/` へ混在させること
- AIエージェント運用系ドキュメントのファイル名に `【AIエージェント運用】` 接頭辞を付けること
- Orval生成物を手動編集すること
- GitHub Actions workflowを仕様書なしで作成・変更すること
- `.github/workflows/` 配下にサブディレクトリを作成すること
- GitHub運用スクリプトを `scripts/` と `.github/scripts/` に無秩序に分散させること
- Git hookを `.github/` や `scripts/` に混在させること
- Cursor専用設定を `prompts/` に配置すること
- 汎用AIプロンプトを `.cursor/` に閉じ込めること
- Task Definitionを `.cursor/` に保存すること
- 成果物正本を `prompts/` に保存すること
- AIログを通常作業サマリの保存場所として濫用すること
- Issue化後の通常作業サマリをすべて `ai-logs/` に保存すること
- worktreeをGit管理対象にすること
- secretやAPIキーをdocs、prompts、ai-logs、Issue、PRに記載すること
- AIの内部推論や長大な生ログをそのまま保存すること
- `.cursorrules` を追加すること

特に重要な設計判断は以下である。

```text
- reco / batch は apps 配下に分離する
- shared logic は packages/shared-logic 配下に切り出す
- API契約は packages/contracts 配下に集約する（ルート openapi/ は採用しない）
- OpenAPI 実ファイルのレイアウトは §8.1.1 に従い Phase1 で実装する
- Phase0 横断パス基準は §8.1.2 を正とする
- コード定義は packages/code-definitions 配下に集約する
- OpenAPIからOrvalでAPIクライアントを自動生成する
- Orval生成物は呼び出し元コンポーネントの generated 配下に配置する
- 生成コードは手動編集しない
- docs 配下のみ日本語ディレクトリ名を採用する
- docs 配下は番号プレフィックス付きで工程順に管理する
- docs/00_共通/プロジェクト管理 にプロジェクト全体の運用ルールを配置する
- docs/00_共通/AIエージェント運用 にAI活用の設計・運用ルールを配置する
- prompts にはAIが実行時に読むDefinitionとテンプレートを配置する
- .cursor にはCursor固有のCommand / Agent / Ruleを配置する
- .githooks にはcommit-msg等のGit hookを配置する
- ai-logs は通常作業ログではなく、Issue化前・例外・横断影響・実験ログに限定する
- GitHub Actions workflowは仕様書を作成してから .github/workflows に実装する
- GitHub運用補助スクリプトは .github/scripts に配置する
- 汎用AI補助スクリプトは scripts/ai に配置する
- worktreeは原則リポジトリ外に配置する
- .cursorrules は採用しない
```
