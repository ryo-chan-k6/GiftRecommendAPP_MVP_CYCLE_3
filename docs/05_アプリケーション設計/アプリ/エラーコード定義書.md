# エラーコード定義書

## 1. 概要

### 1.1 目的

本ドキュメントは、Gift Recommendation Service MVP におけるエラーコード体系を定義する。

本サービスでは、web / api / reco / batch / 外部API連携 / DB / Object Storage など複数コンポーネントが連携するため、エラー表現が分散しやすい。

そのため、本ドキュメントでは以下を明確にする。

```
- エラーコードの命名規則
- エラー分類
- HTTPステータスとの対応
- ユーザー表示メッセージと内部ログの分離
- APIレスポンス形式
- Reco / Batch / 外部API連携で利用するエラーコード
- リトライ可否
- 後続のAPI設計・ログ設計・テスト設計への引き継ぎ事項
```

## 3. エラーコード設計方針

### 3.1 基本方針

| 方針                                | 内容                                                                     |
| ----------------------------------- | ------------------------------------------------------------------------ |
| ユーザー表示と内部原因を分離する    | ユーザーには安全で分かりやすいメッセージを返し、詳細原因はログへ記録する |
| エラーコードは機械判定可能にする    | web / api / reco / batch / test で分岐しやすいコード体系にする           |
| HTTPステータスだけに依存しない      | 同じ400でもValidationエラー、業務ルールエラー、入力形式エラーを区別する  |
| 外部APIエラーを内部コードへ変換する | 楽天API / OpenAI API / StorageなどのエラーをそのままUIへ露出しない       |
| リトライ可否を明示する              | 一時障害か、入力修正が必要なエラーかを区別する                           |
| MVPでは過度に細分化しない           | 初期実装・運用に必要な粒度を優先する                                     |
| 将来拡張可能な体系にする            | 認証、履歴、管理画面、SaaS化に拡張できるようにする                       |

---

### 3.2 ユーザー向けメッセージの原則

ユーザー向けメッセージでは、以下を避ける。

```
- DBエラー詳細
- SQL文
- Stack Trace
- API Key
- Internal API Key
- 外部APIの生レスポンス
- サーバー内部のファイルパス
- モデル名や内部設定IDの詳細
- 推薦アルゴリズム内部の詳細すぎる失敗原因
```

一方、ユーザーには以下が分かるようにする。

```
- 入力を直せばよいのか
- 時間を置いて再試行すればよいのか
- 推薦条件を広げればよいのか
- サービス側の問題なのか
```

## 4. エラーコード命名規則

### 4.1 フォーマット

エラーコードは以下の形式とする。

```
GRS-{DOMAIN}-{NUMBER}
```

例。

```
GRS-VAL-001
GRS-REC-003
GRS-BAT-002
```

---

### 4.2 DOMAIN一覧

| DOMAIN | 分類                   | 主な対象                |
| ------ | ---------------------- | ----------------------- |
| COM    | Common                 | 共通エラー              |
| VAL    | Validation             | 入力検証エラー          |
| AUTH   | Auth / Authorization   | 認証・認可エラー        |
| RATE   | Rate Limit             | 過剰アクセス制御        |
| REQ    | Recommendation Request | 推薦依頼                |
| REC    | Recommendation / Reco  | 推薦実行                |
| RES    | Recommendation Result  | 推薦結果                |
| FDB    | Feedback               | Feedback                |
| ITM    | Item                   | 商品データ              |
| EXT    | External API           | 楽天API等の外部API      |
| RAW    | Raw / Storage          | Raw保存、Object Storage |
| BAT    | Batch                  | Batch実行               |
| DB     | Database               | DBアクセス              |
| CFG    | Config / Master        | 設定・マスタ            |
| LLM    | LLM / Embedding        | OpenAI API、Embedding等 |
| EVAL   | Evaluation             | 評価処理                |
| OBS    | Observability          | ログ・監視              |
| UI     | UI State               | 画面表示用エラー        |

---

### 4.3 NUMBER採番ルール

| 番号帯   | 用途                           |
| -------- | ------------------------------ |
| 001〜099 | 代表的な業務・入力・制御エラー |
| 100〜199 | 外部依存・連携系エラー         |
| 200〜299 | データ不整合・状態不整合       |
| 900〜999 | 想定外・内部エラー             |

例。

```
GRS-REC-001 = 推薦結果0件
GRS-REC-101 = Reco内部APIタイムアウト
GRS-REC-201 = Recommendation Run状態不整合
GRS-REC-999 = Reco想定外エラー
```

## 5. エラーレスポンス標準形式

### 5.1 APIエラーレスポンス

Public API / Internal API のエラーレスポンスは、原則以下の形式とする。

```
{
  "error": {
    "code":"GRS-VAL-001",
    "message":"入力内容を確認してください。",
    "details": [
      {
        "field":"budgetMax",
        "reason":"予算上限は予算下限以上で入力してください。"
      }
    ],
    "retryable":false,
    "traceId":"trace_xxxxxxxxxx"
  }
}
```

---

### 5.2 フィールド定義

| フィールド            | 必須 | 内容                                           |
| --------------------- | ---- | ---------------------------------------------- |
| error.code            | ○    | 本ドキュメントで定義するエラーコード           |
| error.message         | ○    | ユーザーまたは呼び出し元に返す安全なメッセージ |
| error.details         | 任意 | 入力項目単位などの補足                         |
| error.retryable       | ○    | 同条件で再試行可能か                           |
| error.traceId         | ○    | ログ追跡用ID                                   |
| error.internalMessage | ×    | Public APIでは返さない。ログ専用               |

---

### 5.3 Public APIで返してよい情報

| 情報                | Public API返却 |
| ------------------- | -------------- |
| error.code          | ○              |
| user向けmessage     | ○              |
| validation対象field | ○              |
| retryable           | ○              |
| traceId             | ○              |
| stack trace         | ×              |
| SQL error           | ×              |
| 外部API生レスポンス | ×              |
| secret / token      | ×              |
| 内部設定IDの詳細    | 原則×          |

## 26. リトライ方針

### 26.1 リトライ可否の判断

| retryable | 意味                                       | 例                                           |
| --------- | ------------------------------------------ | -------------------------------------------- |
| true      | 同じ条件で再試行すれば成功する可能性がある | timeout, rate limit, DB一時障害              |
| false     | 入力修正・設定修正・データ修正が必要       | validation, not found, unsupported condition |

---

### 26.2 自動リトライ対象

| 対象                   | 自動リトライ | 備考                  |
| ---------------------- | ------------ | --------------------- |
| 外部API timeout        | ○            | 回数制限付き          |
| LLM timeout            | ○            | 回数制限付き          |
| DB接続一時失敗         | ○            | Transaction単位で注意 |
| Object Storage一時失敗 | ○            | Raw重複保存に注意     |
| Validationエラー       | ×            | 入力修正が必要        |
| 認可エラー             | ×            | 権限修正が必要        |
| 0件結果                | ×            | 正常系として扱う      |

## 28. 後続成果物への引き継ぎ

### 28.1 API設計方針書への引き継ぎ

API設計方針書では、以下を反映する。

```
- APIエラーレスポンスは標準形式に統一する
- Public APIでは内部詳細を返さない
- HTTP Statusとerror.codeを併用する
- retryableをレスポンスに含める
- traceIdをレスポンスに含める
```

---

### 28.2 API一覧への引き継ぎ

API一覧では、各APIに以下の列を追加することを推奨する。

| 列                 | 内容                            |
| ------------------ | ------------------------------- |
| 主な正常レスポンス | 成功時の概要                    |
| 主なエラーコード   | 発生し得る代表コード            |
| HTTP Status        | 成功・失敗時のステータス        |

| UI表示分類         | 入力エラー / 0件 / 一時障害など |

---

### 28.3 ログ・Observability設計書への引き継ぎ

ログ・Observability設計書では、以下を反映する。

```
- error_codeをError Logの主要検索キーにする
- traceIdでweb / api / reco / batchの処理を追跡する
- severityを定義する
- retryableをログに保存する
- 外部APIエラーは外部レスポンスをマスキングして保存する
```

---

### 28.4 テスト設計への引き継ぎ

テスト設計では、以下を確認する。

```
- Validationエラー時に正しいerror.codeが返ること
- 0件結果がエラーではなくempty resultとして扱われること
- reco timeout時にGRS-REC-101が返ること
- Feedback重複時にGRS-FDB-003が返ること
- Rate Limit時にGRS-RATE-001が返ること
- Public APIでstack traceやsecretが返らないこと
```

## 30. まとめ

本サービスでは、エラーコードを以下の形式で管理する。

```
GRS-{DOMAIN}-{NUMBER}
```

主要な分類は以下である。

```
COM  = 共通
VAL  = 入力Validation
AUTH = 認証・認可
RATE = Rate Limit
REQ  = Recommendation Request
REC  = Recommendation / Reco
RES  = Recommendation Result
FDB  = Feedback
ITM  = Item
EXT  = External API
RAW  = Raw / Storage
BAT  = Batch
DB   = Database
CFG  = Config / Master
LLM  = LLM / Embedding
EVAL = Evaluation
OBS  = Observability
UI   = UI State
```

重要方針は以下である。

```
- HTTPステータスだけでなく、error.codeで機械判定できるようにする
- ユーザー表示メッセージと内部ログを分離する
- Public APIでは内部詳細を返さない
- traceIdでログ追跡できるようにする
- retryableで再試行可否を明示する
- Recommendation 0件は異常終了ではなく正常系として扱う
- 外部API / LLM / DB / Storageのエラーは内部コードへ変換する
- Error Logと状態遷移を連動させる
```
