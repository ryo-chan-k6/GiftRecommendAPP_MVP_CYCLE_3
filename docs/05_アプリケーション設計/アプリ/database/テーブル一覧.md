# テーブル一覧

## 1. 作成方針

| 観点         | 方針                                                                                                       |
| ------------ | ---------------------------------------------------------------------------------------------------------- |
| 目的         | 物理ER / テーブル定義 / DDL作成の前段として、永続化対象テーブルを一覧化する                                |
| 対象         | MVPで利用するOnline推薦、Batch商品連携、Feature / Semantic、評価、ログ・メトリクス系テーブル               |
| 除外         | メモリ上の一時データ、Object Storage上のRaw JSON本体、APIレスポンスそのもの                                |
| テーブル粒度 | 正本・派生・Snapshot・Log・Metricを混在させず、用途ごとに分離する                                          |
| 状態管理     | 業務状態を持つテーブルは状態カラムを保持する。詳細な遷移履歴は `phase_log` / `error_log` に記録する        |
| Ranking方針  | ランキングはマスタではなくSnapshotとして管理し、`ranking_snapshot` と `item_popularity_signal` に分離する  |
| Feature方針  | User FeatureはOnlineで生成、Item FeatureはBatchで事前生成する。ただし同一Feature Engineの利用を前提とする  |
| Version方針  | Feature生成・正規化・Semantic変換は `semantic_config_version` / `feature_normalization_version` と紐づける |
| 入力hash方針 | Item Feature / Item Embeddingは、元商品データ更新により再生成が必要になるため、入力hashを保持する          |

### 1.1 テーブル仕様書作成時の識別子方針

| 観点 | 方針 |
| ---- | ---- |
| Task識別子 | `TABLE-XXX` は新設せず、物理テーブル名を使用する |
| Task / Issueタイトル | `{物理テーブル名}:{概要}` を基本とする |
| 成果物ファイル名 | `{物理テーブル名}_テーブル定義書.md` を基本とする |
| 正本一覧 | 本ドキュメントの `テーブル名` 列を正本とする |

| 3   | `recommendation_result`      | Recommendation Result      | 内部正本            | ○   | reco         | 推薦結果全体を保存する               |
| 4   | `recommendation_result_item` | Recommendation Result Item | Snapshot / 内部正本 | ○   | reco         | 推薦結果に含まれる商品明細を保存する |

### 補足

| 論点                               | 方針                                                                                                                                                                                                                                               |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `recommendation_request` の `mode` | `ui` / `evaluation` / `batch` を保持する                                                                                                                                                                                                           |
| budget条件                         | `recommendation_request` に `budget_min` / `budget_max` として保持する                                                                                                                                                                             |
| request conditionの扱い            | MVPでは独立テーブル化せず、`recommendation_request` 内のカラムまたはJSONで保持する                                                                                                                                                                 |
| result item snapshot               | 商品名、価格、URL、画像URLなどは推薦結果表示時点で固定する                                                                                                                                                                                         |
| 0件結果                            | errorではなく、`recommendation_result` の正常なempty resultとして扱う                                                                                                                                                                              |
| Relationship / Occasion / Pair     | ユーザー入力としては `relationship_id` と `occasion_id` を受け取り、処理時に `pair_master` から `pair_id` を解決する。推薦再現性を重視するため、`recommendation_request` または `recommendation_run` に解決済み `pair_id` を保持することを検討する |

### 補足

| 論点                                | 方針                                                                                                                                               |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `semantic_config_version`           | Feature生成・正規化・Social/Symbolic射影の意味体系versionとして扱う                                                                                |
| Public 参照（Semantic Config）      | `config_name`（親 `semantic_config` 正本）+ `version_label`（本テーブル）の composite。api（IF-DB-API-005）はアプリ層 JOIN で解決。DB ビュー・version 表への `config_name` denormalize は行わない |
| MVP 初期 `version_label`            | semver 形式 `v1.0.0`（`semantic_config_version_テーブル定義書` §17.1 参照）                                                                      |
| `model_version`との違い             | `semantic_config_version` は意味の作り方、`model_version` はRanking・Embedding・理由生成等のモデルversion                                          |
| Feature軸                           | MVPでは8次元固定                                                                                                                                   |
| `feature_rule`                      | 論理ER上の抽象名。物理テーブルでは `relationship_rule` / `occasion_rule` / `pair_rule` / `lambda_ctx_rule` / `concept_feature_rule` 等へ分解する                       |
| NG条件                              | Feature化せずHard Filterで扱う                                                                                                                     |
| budget条件                          | Feature化せずHard Filterで扱う                                                                                                                     |
| `pair_master` と `pair_rule` の違い | `pair_master` は Relationship × Occasion の組み合わせ自体を管理するマスタであり、`pair_rule` はそのPairに対してFeature補正値を定義するルールである |
| `lambda_ctx_rule` と `user_meaning.lambda_ctx` | `lambda_ctx_rule` は Rule Lookup 設定正本。`user_meaning.lambda_ctx` は MOD-RECO-009 算出結果の Run 固定列（Issue #843） |
| `concept_feature_rule` 物理参照 | 論理 `concept_code` は物理列 `semantic_concept_id`（`semantic_concept` FK）。API `conceptCode` は JOIN 導出。`feature_delta` は 0.0〜1.0（大きさ）、`polarity` で方向表現。MVP seed は 18 Concept 対象の稀疏投入（`concept_feature_rule_テーブル定義書` §17.1） |
| `normalization_rule` と `feature_normalization_version` | `normalization_rule` は意味 version への **binding**（方式 + version 参照）。`feature_normalization_version_id` は **物理 FK ON**。sigmoid パラメータ正本（`parameter_json`）は `feature_normalization_version`（`normalization_rule_テーブル定義書` §5.1 / §8） |

## 12. 非DB管理対象

| 対象                  | 保存先                         | テーブル化しない理由                                       |
| --------------------- | ------------------------------ | ---------------------------------------------------------- |
| Raw Product Object    | Object Storage                 | Raw JSON本体は容量が大きく、DBにはMetadataのみ保持するため |
| Normalized Payload    | memory / staging JSON          | 差分判定・変換処理中の一時データであり、正本ではないため   |
| API Response Body全文 | Object Storage / 必要時のみlog | DB肥大化を避けるため                                       |
| Feature計算途中値     | memory / 必要時debug log       | 推薦結果の再現に必要な最終値のみ保存すればよいため         |
| LLM prompt全文        | 原則非保存 / 必要時マスク保存  | 個人情報・自由入力・コスト面の懸念があるため               |
