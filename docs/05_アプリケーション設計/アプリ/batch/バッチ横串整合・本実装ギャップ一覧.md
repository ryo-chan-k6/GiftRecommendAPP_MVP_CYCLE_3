### 4.2 設計上「複合」だが実装は独立子の例

| 設計表記 | 実装の事実 |
| -------- | ---------- |
| `batch-rakuten-existing-item-recheck.yml` = 004〜008/017 複合 | 実ファイルは **BATCH-004 単独**の独立子 |
| 各 Batch の親接続 | 各仕様 §18 で「独立子を正・親全体改修は Epic 外／後続」と確定 |

### 4.3 依存関係・スケジュールとの差分

| 観点 | 設計 | 実装（E1 後） |
| ---- | ---- | ---- |
| 起動 | 親の `schedule` のみ | 親 YAML は作成済み。Phase1 は `on.schedule` 無効のため定期起動なし（`workflow_dispatch` で検証） |
| 先行関係 | 親内 `jobs.needs` | 親／複合子内で `needs` 配線済み。実ランタイム検証（dry-run）は未実施 |
| 子の trigger | `workflow_call` + `workflow_dispatch` | 19 本とも同方針（独立 cron なし）。複合子も `workflow_call` / `workflow_dispatch` |
| 失敗時 | 先行失敗で後続停止 | YAML 上は `needs` による停止を定義。親単位の実運用検証は未実施 |

**事実:** E0 時点の intentional gap（親／複合未作成）は E1 で解消。残ギャップは Phase2/3 の schedule 有効化と実ランタイム検証、および E2〜E4。
