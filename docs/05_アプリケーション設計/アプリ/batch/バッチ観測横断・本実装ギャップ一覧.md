## 4. IF / MOD × 実装突合（事実）

### 4.1 横断モジュール・IF

| ID | 名称 | 主テーブル | 実装の事実 | ギャップ |

## 8. Human 判断点（Epic #1636 §11 / Epic Def）— **確定済み**

### 8.1 必須最小 Batch 範囲

| 案 | 内容 | メリット | デメリット |
| -- | ---- | -------- | ---------- |
| A | 取込一部 + meaning/feature 代表 + 017（§7 案 A） | 早く代表経路で観測確認できる | 外部 API 失敗の DB 追跡は後回しになりうる |
| B | A + 外部 API 代表（001 または 015） | Rate Limit / EXT 失敗の調査が可能 | Wave 3 とセットで工数増 |
| C | 001〜017 全適用 | 横断揃え完了に近い | MVP 期間・レビュー負荷が大きい |

**Human 確定（2026-07-28）:** 案 **C**。時間がかかっても BATCH-001〜017 全適用で進める。018/019・043/044 へは混入しない。

### 8.2 `api_call_log` を E4 必須に含めるか

| 案 | 内容 | メリット | デメリット |
| -- | ---- | -------- | ---------- |
| Must | Wave 3 を必須 | 楽天 / Embedding 障害解析が DB で完結 | 実装・UT・疎通が増える |
| Optional（後続） | E4 最小は Run/Phase/Error。API Call は別 Task / follow-up | 最小完了が早い | 外部失敗はアプリログ依存が残る |
| Out | E4 から除外し別 Epic | 境界明確 | Observability 正本の「必須」表記と乖離しうる |

**Human 確定（2026-07-28）:** **Must**。Wave 3（IF-002 / MOD-046）を E4 必須とする。

### 8.3 #1623 / 書込 Epic との着手順

| 案 | 内容 | メリット | デメリット |
| -- | ---- | -------- | ---------- |
| A | SELECT・書込完了済みを前提に **E4 実装へ進む** | 依存待ちが少ない | 書込 Epic の develop 未統合があれば tip 差分に注意 |
| B | 書込 / SELECT の develop 統合完了を厳密ブロック | tip 一貫・依存の再作業を避けやすい | E4 着手が遅れる |
| C | SELECT 未完了 Batch と並行で観測だけ先行 | 早期可視性 | run 紐づけ・summary 入力が不安定 |

**Human 確定（2026-07-28）:** 案 **B**。時間より安全・確実を優先し、#1623（SELECT）および書込 Epic（#1632〜#1635）の **develop 統合完了を厳密ブロック**としてから E4 実装 Wave（Wave 1 以降）に着手する。

**ブロック解除の確認観点（推論）:** develop 上で SELECT / 書込の本線が揃っていること、親 Epic tip と tip 差分が運用上許容できること。未統合のまま Wave 1 に入ると、観測配線のやり直しコストが出やすい。
