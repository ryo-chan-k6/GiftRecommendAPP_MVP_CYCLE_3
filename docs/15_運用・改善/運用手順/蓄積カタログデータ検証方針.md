本書は、バッチ運用検証と並行して行う **カタログデータ検証** の範囲・合格ライン・禁止事項を正本化する。
詳細な採択記録は [Human Decision Log](../../../ai-logs/human-decisions/2026-08-25-catalog-data-verification-policy.md) とする。
secret、接続文字列、token などの実値は記載しない。

チャット上の同意だけでは正本としない。本docsと上記 Decision Log を正本とする。

---

## 2. 目的

local に蓄積した楽天実データが、アプリの商品正本として最低限使えるかを、レコメンド品質評価（本線#7）の前に確認する。

バッチ Run の成功と、カタログの健全性は分けて扱う。

---

## 3. 適用範囲

### 3.1 対象

- 対象環境: **local DB のみ**
- 対象データ: 楽天 Fetch → Staging → Item 反映済みのカタログと、意味連鎖の派生データ
- 検証層: 案B（§4）

### 3.2 対象外

| 対象 | 理由 |
| ---- | ---- |
| stgレコメンド品質評価（#1745 本線#7） | 別レーン。本方針では起票しない |
| reco / api / web からの推薦実行 | 第一波の完了条件にしない |
| 簡易stgデータ投入（#1795） | 別Issue。local蓄積データの検証ではない |
| fetch_plan 変更・追加 live 収集 | 発見があっても本方針では変更しない |
| AI による `--live-rakuten` | 禁止維持 |
| 定常 crontab（#1811） | 変更しない。運用検証は止めない |
| GHA 楽天 live / #1607 / #1792 | 対象外維持 |
| DB schema / migration / 破壊的更新 | 読み取り検証のみ |
| `apps/web` / `apps/api` / `apps/reco` / `apps/batch` の実装改修 | 発見時は別Issue |

## 4. 採択方針（案B）

Human 採択（2026-08-25）は **案B** である。

| 案 | 内容 | 採否 |
| --- | ---- | ---- |
| A | パイプライン整合 + 意味カバレッジのみ | 不採択 |
| **B** | A に加え、贈答適否の観点定義と少数サンプリング（reco実行なし） | **採択** |
| C | 本線#7（stgレコメンド品質評価）まで含める | 不採択 |

---

## 5. 検証の3層

| 層 | 内容 | 第一波 |
| --- | --- | --- |
| A. パイプライン整合 | Raw / Staging / Item の漏れ、必須項目、画像、ジャンル、価格外れ値 | 実施（snapshot Task） |
| B. 意味連鎖カバレッジ | `item_generation_queue` / `item_semantic` / `item_feature` / `item_meaning` / `item_embedding` | 観測。全件完了は待たない |
| B+. 贈答適否サンプリング | ジャンル・価格帯の疑いリストと少数例 | 実施。最終ラベルは Human |
| C. 推薦品質 | 理由文・人手評価・reco実行 | 本線#7。本方針の対象外 |

層Cを第一波に混ぜない。意味連鎖がカタログに対して少数でも、層A/B/B+は実施してよい。

---

## 6. 第一波合格ライン

| 項目 | 合格ライン | 未達時 |
| ---- | ---------- | ------ |
| staging にあって item に無い商品コード | **0 を維持** | 別Issue化を検討（本方針では修正実装しない） |
| `item_name` / `price` / `item_url` の欠損 | **0** | 同上 |
| 画像なし item | **件数を監視** | 閾値はスナップショット後に Human 判断 |
| `external_genre_id` NULL | **件数を監視** | 同上 |
| 意味連鎖カバー率 | **記録する** | 全件完了不足を第一波の不合格にしない |
| 贈答適否サンプル | **観点どおり少数を記録** | 最終ラベルと収集方針見直しは Human。本方針では fetch_plan を変えない |

スナップショット結果の正本は、後続 Task が `docs/15_運用・改善/運用手順/蓄積カタログデータ検証スナップショット.md` に置く。

## 7. 贈答適否サンプリングの観点（第一波）

実サンプリングは snapshot Task で行う。本節は観点のみを固定する。

| 観点 | 見るもの | 第一波でやらないこと |
| ---- | -------- | -------------------- |
| ジャンル | 贈答から外れて見える上位ジャンル（作業用品・日常衣料など） | 適否の AI 最終確定 |
| 価格 | 極端な安値・高値の件数と代表例 | 価格帯の運用上限変更 |
| サンプル粒度 | 疑いジャンルから少数（数十件規模を上限の目安） | 全件目視、商品名の大量転記 |
| 記録 | genre_id、件数、価格帯、`item_id` の少数例 | URL・接続情報・secret |

最終ラベルは Human が付ける。AI は「疑い」の整理までとする。

## 8. 環境と実行境界

| 項目 | 方針 |
| ---- | ---- |
| DB | local のみ。stg / production へ接続しない |
| バッチ cron | **止めない**。SELECT は Run と並行してよい |
| SQL | 読み取り専用。書き込み・TRUNCATE・全件 UPDATE は禁止 |
| 繰り返し用SQL | 置く場合は `scripts/db/catalog-data-verification*` のみ |
| 観測日時 | 結果docsに JST で記録する |
