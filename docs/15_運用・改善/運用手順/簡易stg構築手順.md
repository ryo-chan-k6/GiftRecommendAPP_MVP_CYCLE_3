## 4. 目標構成（MVP 簡易 stg）

用語: 「簡易 stg」＝環境設計書の `stg`＝全体テスト計画書の `staging`（受入環境方針）。

| コンポーネント | MVP 方針 | 想定プラットフォーム（例） |
| --- | --- | --- |
| Web | あり | Vercel（Environment: stg） |
| API | あり | Render 等（Environment: stg） |
| Reco | あり | Fly.io 等（Environment: stg） |
| Batch | あり（手動＋必要なら一部定期） | GitHub Actions |
| PostgreSQL | **stg 専用 1 本**。prod/local/Layer2 と共有しない | Supabase なら **stg 用プロジェクト 1** |
| Redis | 環境ごと分離 | **Upstash Redis**（stg 専用 DB。[デプロイ設定書](../../14_リリース/デプロイ設定/デプロイ設定書.md) H-DEP-01） |
| Object Storage | 環境ごと分離。`raw-products` 等は private | Supabase Storage（stg プロジェクト内） |
| 監視 | 最小〜中 | プラットフォーム標準ログで可 |

確定詳細（受入環境方針 §7）:

- schema は **prod と同一 migration**
- Replica / 分析分離は持たない
- 同一 DB 内に master / 縮小カタログ / 評価セット / 実行ログ
- api / reco /（必要なら）batch は **同一の stg `DATABASE_URL`**
- 外部 API live は既定 off。限定 live は明示時のみ

## 5. 前提（着手前）

1. [受入環境方針](../../13_受入テスト/テスト計画/受入環境方針.md) の採用方針を確認する
2. [環境変数定義書](../../06_実装設計/cross_cutting/環境変数定義書.md) の変数名を確認する
3. [環境変数運用手順](./環境変数運用手順.md) の登録・分離確認の流れを把握する
4. prod / local の secret を stg 作業端末のメモやチャットに置かない
5. カタログ件数目安は Human が別途確定してよい（未確定でも手順は進められる）

## 9. 構築完了の定義

次をすべて満たしたとき、**簡易 stg 構築完了**とする。

1. §6 の該当チェックが完了している
2. §7（環境変数運用手順の登録・分離・受入前確認）が完了している
3. §8 の疎通が Pass している
4. 実施者が「実施環境 = 簡易 stg」と分かる記録を残せる状態である（受入結果・リリース判定の入力）

受入テストケース全量の実施、システム／品質本実施、prod 構築は含まない。
