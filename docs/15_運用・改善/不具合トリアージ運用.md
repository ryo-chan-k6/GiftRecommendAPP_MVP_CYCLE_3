## 2. 目的

- 不具合の重大度（Severity）を共通言語で分類できるようにする
- 起票 → トリアージ → 修正 → 再確認 → リリースゲート確認の手順を固定する
- リリース判定チェックリストの「不具合」行が、証跡付きで埋められるようにする

---

## 3. Severity 定義（草案）

全体テスト計画書 §11.1 を起点とする。**最終文言の確定は Human**（本節は草案）。

| 重大度 | 定義（草案） | リリース可否（§11.1） |
| --- | --- | --- |
| Critical | レコメンド実行不可、DB破壊、主要 Batch 実行不可、主要 API 契約破壊、重大なセキュリティ問題 | **不可** |
| High | 推薦結果が大きく不正、Feature 生成不正、主要ログ欠落、再実行不能、SLO 大幅未達、生成 client と API 実装の不整合 | **原則不可** |
| Medium | 一部条件で表示不備、軽微なランキング不整合、運用回避可能な Batch 失敗、API client wrapper の軽微な不整合 | 判断 |
| Low | 文言、軽微な UI、内部ログの軽微な不足 | 可 |

### 3.1 Severity と Issue `priority:*` の区別（重要）

| 概念 | 意味 | 既存ラベル例 |
| --- | --- | --- |
| **Severity（重大度）** | 欠陥がユーザー／システム／契約に与える影響の大きさ。リリースゲート判定に使う | **専用ラベルは未整備**（草案。Human が新設要否を判断） |
| **priority（作業優先度）** | いつ着手するかの順序。Issue運用ルールの必須ラベル | `priority: critical` / `high` / `medium` / `low` |

同一 Issue で両方が高くなることが多いが、**混同しない**。  
例: Severity=High でも、回避策がありリリース後対応と Human が決めた場合、作業 `priority` を下げうる（その場合も Severity=High のままならリリースゲート上は残件）。

## 4. 不具合管理項目（必須最小）

全体計画 §11.2 を運用最小に落とす。Issue 本文またはテンプレ欄に含める。

| 項目 | 内容 |
| --- | --- |
| 不具合ID | GitHub Issue 番号 |
| 発見フェーズ | 技術検証／単体／結合／システム／非機能／品質評価／受入／運用 |
| 対象コンポーネント | web / api / reco / batch / shared_logic / DB 等 |
| Severity | Critical / High / Medium / Low（本運用の分類） |
| 作業 priority | `priority:*` ラベル（Issue運用） |
| 再現手順 | 入力・環境・操作 |
| 期待／実際 | 期待結果と実際結果 |
| API契約関連 | 該当時: OpenAPI / Orval / generated / typecheck のどこで検知したか |
| 関連ログ | `trace_id` / `run_id` / `batch_run_id` / `error_code`（秘密情報は貼らない） |
| 対応状況 | Open / In Progress / Fixed / Retest / Closed |

## 5. 推奨ラベル・Projects 扱い

### 5.1 既存で使うもの

| 用途 | 推奨 |
| --- | --- |
| 不具合修正 Issue | `type: fix`（既存 `bug` ラベルがある場合は併用可。新規 Task 作業は Issue運用の必須セットに従う） |
| 作業優先度 | `priority: critical` / `high` / `medium` / `low` |
| 領域 | `area:*`（api / reco / batch / web 等） |
| Projects Status | 通常の Task と同様（In Progress → …）。**Severity は Status に載せない** |

### 5.2 Severity ラベル（草案・Human 未確定）

| 案 | 内容 | 利点 | 欠点 |
| --- | --- | --- | --- |
| A. `severity: critical` 等を新設 | Issue 一覧で Severity=0 をフィルタしやすい | ゲート確認が機械的 | label 運用が増える。`priority: critical` と紛らわしい |
| B. Issue 本文の Severity 欄のみ | ラベル追加なし | Issue運用変更が小さい | 一覧フィルタが弱い |
| C. Projects カスタムフィールド | Severity を Project 列に持つ | 可視化しやすい | フィールド追加の運用コスト |

**推奨（AI）:** MVP 初期は **案 B**（本文必須）＋必要なら後で案 A。確定は Human。

label の **実作成は本 Task の out of scope**（Human 承認後の別 chore）。

## 6. 手順（起票〜リリースゲート）

```text
発見
  → Issue 起票（type: fix 等＋§4 項目）
  → トリアージ（Severity 仮付け → Human 確定）
  → 修正 Branch / PR（通常の fix 運用）
  → Fixed / Retest（再現確認・回帰）
  → Closed（残 Critical/High から除外）
  → リリース判定前: Critical/High の Open 残件 = 0 を確認
```

### 6.1 トリアージ窓口

| 項目 | 方針 |
| --- | --- |
| 一次トリアージ | 発見者または担当 AI／Human が Severity を **仮付け** |
| 確定 | Critical / High は原則 **Human が確定**（AI は案のみ） |
| 記録場所 | Issue 本文の Severity 欄＋コメント（変更理由） |
| ダウングレード | Critical/High → Medium/Low は Human のみ。理由をコメント必須 |

### 6.2 リリースゲートでの確認手順

リリース判定（§12.2「不具合」）直前に、次を実施する。

1. Critical / High として管理されている Issue を洗い出す（本文 Severity、または Human 確定後のラベル）
2. 状態が Open / In Progress / Fixed（未 Retest）/ Retest のものを **残件** と数える
3. Closed のみを 0 件側に含める（再発 Issue は新規として再カウント）
4. 残件数をリリース判定チェックリストの「不具合」行に記入し、証跡として Issue 検索 URL または一覧をリンクする
5. Critical / High が 1 件以上残る場合、リリース不可（または Human がスコープ延期を明示）

Medium / Low の残件はリリースを自動で止めない。既知制約としてリリースノート／判定メモへ載せる。

### 6.3 「0件」の定義（運用）

| 含める | 含めない |
| --- | --- |
| Severity=Critical または High かつ未 Closed | Medium / Low |
| Fixed だが Retest 未完了 | 別プロダクト・スコープ外と Human が明示したもの |
| 再現不能でも未クローズの Critical/High | 誤起票として Human がクローズしたもの |

## 8. secret / セキュリティ

- Issue・コメント・証跡に secret、token、`.env` 実値、個人情報を書かない
- ログ貼付時は `Authorization` ヘッダ・接続文字列・API key をマスクする
- セキュリティ系 Critical は公開 Issue 本文を最小にし、必要なら限定共有（詳細は Human）
