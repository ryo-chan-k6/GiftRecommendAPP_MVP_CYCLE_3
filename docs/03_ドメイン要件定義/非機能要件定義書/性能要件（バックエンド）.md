## 4. レコメンド処理時間内訳（重要）

レコメンドAPIのレスポンスは以下の分解で設計する。

```
API受信
↓
Reco処理
  ├ 入力解析
  ├ User Meaning推定
  ├ Candidate Retrieval
  ├ Ranking
↓
レスポンス生成
```

---

### 4.1 各ステップの目標時間

| ステップ | 目標時間 | 備考 |
| -------- | -------- | ---- |
| 入力解析 | 50ms | Reco 内部 |
| Meaning推定（User Meaning・同期外部 AI） | **4,000ms**（典型） / hard **5,000ms** | cold path 前提。Phase2 secrets 約 3.5–4.3s |
| Retrieval | 300ms | Reco 内部。hard 1,000ms |
| Ranking | 300ms | Reco 内部。hard 1,000ms |
| レスポンス整形 | 50ms | Output。`phase_output`（Reason）上限は別 Task |

👉 本番主経路の合計目標: soft **6,000ms** / hard **8,000ms**（MOD-RECO-001 §13.2）。Reco 内部のみの監視目標: soft **1,500ms** / hard **2,000ms**。

**注記（Phase2）:** mock 実測のパイプライン合計は約 450–700ms（内部 Go）。secrets では User Meaning が支配。

## 5. タイムアウト設計

正本のフェーズ別 hard / soft 詳細は **MOD-RECO-001 §13.2** と整合させる。PoC 根拠: [Reco性能フィジビリティ検証結果_Phase2_live](../../90_PoC/性能フィジビリティ/Reco性能フィジビリティ検証結果_Phase2_live.md)、[設計反映メモ](../../90_PoC/性能フィジビリティ/設計反映メモ.md)。

**ステータス:** #1533 Human 確定反映済み（`phase_output` のみ別 Task）。

### 5.1 APIタイムアウト

| 対象 | タイムアウト | 備考 |
| ---- | ------------ | ---- |
| 外部API（recommendations） | **10秒** | Public 境界。Reco hard 8s + オーバーヘッド |
| 内部Reco API | **8秒** | MOD-RECO-001 同期外部 AI 込み hard 8,000ms / `GRS-REC-101` と整合 |

---

### 5.2 Recoタイムアウト（Human 確定値）

| 処理 | タイムアウト | MOD-RECO-001 §13.2 | 備考 |
| ---- | ------------ | ------------------ | ---- |
| soft（Reco 内部） | **1.5秒** | 内部 soft 1,500ms | 監視用 |
| hard（Reco 内部） | **2秒** | 内部 hard 2,000ms | 監視用 |
| soft（同期外部 AI 込み） | **6秒** | 本番主経路 soft | Phase2 secrets + 余裕 |
| hard（同期外部 AI 込み） | **8秒** | 本番主経路 hard / ウォッチドッグ | §5.1 内部 Reco と一致 |
| Config 解決 | 300ms | phase_config | 維持 |
| Meaning推定（User Meaning） | **5秒** | phase_user_meaning | 同期・cold path |
| Retrieval | 1秒 | phase_retrieval | 維持 |
| Matching | 500ms | phase_matching | 維持 |
| Ranking | 1秒 | phase_ranking | 維持 |
| Output（Reason 含む） | **未確定**（当面 500ms 記載） | phase_output | **別 Task** |

---

### 5.3 タイムアウト時の挙動

```
・run_event_logにtimeout記録
・エラー応答を返す（500系）
・ユーザーには再試行可能なメッセージ表示
```

全体 hard（同期外部 AI 込み **8,000ms**）超過時の Reco 側エラーコードは `GRS-REC-101`（MOD-RECO-001 §13）。API 層の HTTP マッピングは契約仕様に従う。

---

### 5.4 Human 確定方針（#1533）

| 区分 | 確定内容 |
| ---- | -------- |
| 分離 | Reco 内部 / 同期外部 AI を分けて soft・hard を定義 |
| UX | User Meaning は **同期**。非同期は主方針にしない |
| cold path | 検索条件の組み合わせは毎回新しくなり得る前提。キャッシュは補助のみ |
| Reason（`phase_output`） | 本 Task では未確定。**別 Task 起票** |

実装・クライアントの timeout 定数が旧 4s / 5s のままの場合は、本節への追従を別実装 Task とする。

### 7.1 キャッシュ対象

| 対象            | 方針           |
| --------------- | -------------- |
| 商品embedding   | キャッシュ     |
| retrieval結果   | 短期キャッシュ |
| semantic_config | 常駐           |

---

### 7.2 キャッシュTTL

| 対象            | TTL                        | 更新トリガー                    | 設計意図                                     |
| --------------- | -------------------------- | ------------------------------- | -------------------------------------------- |
| 商品embedding   | **24時間（86400秒）**      | BTでembedding再生成時に強制更新 | 商品情報は頻繁に変わらないため長期キャッシュ |
| retrieval結果   | **5分（300秒）**           | TTL満了 or キャッシュミス       | 同一条件の短時間再検索を高速化               |
| semantic_config | **無期限（プロセス常駐）** | config更新時に即時リロード      | 実行時の安定性・高速化                       |
| model_version   | **無期限（プロセス常駐）** | version切替時に即時反映         | 推論ロジックの一貫性確保                     |

## 15. 設計原則（性能）

```
・レコメンド本番経路は同期（UX優先）。User Meaning も同期・cold path 前提
・Reco 内部の監視目標は soft 1.5s / hard 2s
・同期外部 AI 込みの本番目標は soft 6s / hard 8s
・Item Meaning 等の重い前処理は BT へ逃がす
・キャッシュは補助（User Meaning SLO の主前提にしない）
・Reproducibilityを優先
・フォールバック必須
```

レコメンドは同期で結果を返し、
