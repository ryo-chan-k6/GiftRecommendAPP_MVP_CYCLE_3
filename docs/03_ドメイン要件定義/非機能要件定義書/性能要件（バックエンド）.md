## 4. レコメンド処理時間内訳（重要）

レコメンドAPIのレスポンスは以下の分解で設計する。

```
API受信
↓
Reco処理
  ├ 入力解析
  ├ User Meaning推定
  ├ Candidate Retrieval
  ├ Ranking
↓
レスポンス生成
```

---

### 4.1 各ステップの目標時間

| ステップ       | 目標時間 |
| -------------- | -------- |
| 入力解析       | 50ms     |
| Meaning推定    | 300ms    |
| Retrieval      | 300ms    |
| Ranking        | 300ms    |
| レスポンス整形 | 50ms     |

👉 合計目標：1,000ms前後（通常）

**注記（Phase2）:** mock 実測のパイプライン合計は約 450–700ms 帯で目標に近い。secrets では User Meaning（外部 AI）が支配し、本表の Meaning 推定 300ms とは乖離する。Orchestrator フェーズ hard の正本は MOD-RECO-001 §13.2。

## 5. タイムアウト設計

正本のフェーズ別 hard / soft 詳細は **MOD-RECO-001 §13.2** と整合させる。PoC 根拠: [Reco性能フィジビリティ検証結果_Phase2_live](../../90_PoC/性能フィジビリティ/Reco性能フィジビリティ検証結果_Phase2_live.md)、[設計反映メモ](../../90_PoC/性能フィジビリティ/設計反映メモ.md)。

**ステータス:** TV-007 Phase2 完了後の正式反映。現行数値は運用基準として維持し、**最終採否は Human Review（§5.4）**。

### 5.1 APIタイムアウト

| 対象                       | タイムアウト | 備考 |
| -------------------------- | ------------ | ---- |
| 外部API（recommendations） | 5秒          | Public 境界 |
| 内部Reco API               | 4秒          | MOD-RECO-001 全体 hard 4,000ms / `GRS-REC-101` と整合 |

---

### 5.2 Reco内部タイムアウト（現行運用値・Human 確定待ち）

| 処理 | タイムアウト | MOD-RECO-001 §13.2 対応 | Phase2 所見（要約） |
| ---- | ------------ | ----------------------- | ------------------- |
| soft（全体 p95） | 2秒 | soft 2,000ms | mock: Go / secrets: 未達 |
| hard（全体） | 4秒 | hard 4,000ms | secrets: GHA Block / local Adjust |
| Config 解決 | 300ms | phase_config | 維持候補 |
| Meaning推定（User Meaning） | 1秒 | phase_user_meaning | secrets で大幅超過 → **Adjust 候補** |
| Retrieval | 1秒 | phase_retrieval | 余裕（seed 3 件）→ 維持候補 |
| Matching | 500ms | phase_matching | 余裕 → 維持候補 |
| Ranking | 1秒 | phase_ranking | 余裕 → 維持候補 |
| Output（Reason 含む） | 500ms | phase_output | 参考計測で超過 → **Adjust 候補**（TV-007 主対象外） |

---

### 5.3 タイムアウト時の挙動

```
・run_event_logにtimeout記録
・エラー応答を返す（500系）
・ユーザーには再試行可能なメッセージ表示
```

全体 hard 超過時の Reco 側エラーコードは `GRS-REC-101`（MOD-RECO-001 §13）。API 層の HTTP マッピングは契約仕様に従う。

---

### 5.4 Phase2 反映方針（AI 推奨・Human 確定待ち）

| 区分 | 扱い | AI 推奨（推論） |
| ---- | ---- | --------------- |
| Reco 内部（Config / Retrieval / Matching / Ranking） | soft/hard・フェーズ上限 | **Go 寄り・現行値維持候補** |
| 外部 AI（User Meaning / Reason） | 同期 LLM 遅延 | **Adjust**（上限見直し・キャッシュ・非同期等）。全体 SLO を「外部 AI 込み」で定義するか分離するかは Human 判断 |

Human Review で確認する論点:

1. 「内部 Go / 外部 AI Adjust」分離の採否
2. soft 2,000ms / hard 4,000ms の維持 or 見直し
3. `phase_user_meaning` / `phase_output` 上限

## 7. キャッシュ戦略

### 7.1 キャッシュ対象

| 対象            | 方針           |
| --------------- | -------------- |
| 商品embedding   | キャッシュ     |
| retrieval結果   | 短期キャッシュ |
| semantic_config | 常駐           |
| model_version   | 常駐           |

---

### 7.2 キャッシュTTL

| 対象            | TTL                        | 更新トリガー                    | 設計意図                                     |
| --------------- | -------------------------- | ------------------------------- | -------------------------------------------- |
| 商品embedding   | **24時間（86400秒）**      | BTでembedding再生成時に強制更新 | 商品情報は頻繁に変わらないため長期キャッシュ |
| retrieval結果   | **5分（300秒）**           | TTL満了 or キャッシュミス       | 同一条件の短時間再検索を高速化               |
| semantic_config | **無期限（プロセス常駐）** | config更新時に即時リロード      | 実行時の安定性・高速化                       |
| model_version   | **無期限（プロセス常駐）** | version切替時に即時反映         | 推論ロジックの一貫性確保                     |


## 15. 設計原則（性能）

```
・同期処理は2秒以内を目標
・重い処理はBTへ逃がす
・キャッシュを積極利用
・Reproducibilityを優先
・フォールバック必須
```

---

# 16. 一言まとめ

```
レコメンドは同期で高速応答しつつ、
重い処理は事前計算・キャッシュ・並列化で吸収し、
最悪でもフォールバックで結果を返す設計とする
```
